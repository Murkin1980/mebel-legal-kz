## Известный дрейф

Удалённая таблица `supabase_migrations.schema_migrations` исторически содержит только
`001` и две новые timestamp-версии. Схема при этом содержит объекты миграций 002–029,
которые ранее применялись вручную/объединёнными SQL-файлами.

До отдельной инвентаризации запрещено:

- выполнять `supabase db push --include-all`;
- массово отмечать 002–029 как applied;
- повторно запускать старые combined-миграции;
- удалять или переименовывать существующие таблицы.

## Рекомендуемое восстановление истории

1. Сделать логический backup в среде с Docker/Postgres tooling.
2. Снять schema-only dump удалённой базы.
3. Сопоставить каждый объект с 002–029 и combined-файлами.
4. Проверить результат на отдельном Supabase branch.
5. Только после доказанного совпадения выполнить точечный `migration repair`.
6. Включить миграции в CI и применять их одним владельцем релиза.

Новые изменения после 26 июля должны оформляться отдельными timestamp-миграциями.
